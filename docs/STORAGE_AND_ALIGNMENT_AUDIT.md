# 缓存策略与对齐接入核查（2026-09-23）

## 存储分类

| 内容 | 生命周期 |
| --- | --- |
| 原片、字幕、模型权重、运行环境、显式导出 | 持久数据，缓存清理从不触碰 |
| 已保存采样绑定音频、有效分离轨、分析测量、原始对齐输出、来源清单 | 持久结果；沿数据库引用和结果清单保留，不因过期重算模型 |
| 裁切/解码 PCM、浏览器转码、卡拍试听音频 | 按需生成和复用；无持久引用时可清理 |
| 波形、频谱、缩略图、派生节奏方案 | 可重建缓存，清理不会启动模型或新增采样 |
| 已退休工具输出、旧实验结果、未引用的中间处理音频 | 手动清理时删除；不是通过隐藏入口继续留存 |
| FCPE 等已有声学测量 | 保留，避免把查看波形变成重新推理 |
| 小型播放器描述文件 | 保留，避免清缓存使已打开的播放器引用失效 |
| 环境安装包缓存 | 本次单独清理，不删环境内文件；以后安装完成后可再次清理 |

设置 → 存储与缓存：显示各类占用和可清理容量。清理只扫描固定生成目录，不接受用户传入任意目录，不穿越符号链接。正在运行或排队的任务阻止清理；最近 15 分钟生成的文件暂留；文件在扫描后被改写则跳过。清理与任务提交共用维护锁，并在引用快照和删除期间持有数据库写事务。每次清理记录实际删除路径及跳过项到 `data/maintenance`，不备份大文件。

可关闭的“空闲时整理可重建缓存”：服务连续 5 分钟没有请求、没有任务时，每小时最多检查一次，清掉超过 7 天或使未引用的廉价缓存超过 2 GiB 的最老文件。GUI 轮询也算活动，宁可暂留也不在用户操作中自动清理。最近 15 分钟文件和持久引用优先保护，所以 2 GiB 不是强制硬上限，更不是整个项目的上限。自动整理不删昂贵的模型处理输出。

整片人声、残差和 BandIt 三轨属于可复用资产，不应每次试听/对齐重做。模型输入裁切可以短期缓存；仍被旧分析清单或采样方案直接引用的 PCM 暂时保留。后续再把这些旧引用改成可重建的媒体描述，才能进一步回收，不能直接破坏当前结果。

独立字幕预处理的 `outputs/subtitle-preprocessing` 保留：它包含预处理所需的人声输出和最终字幕，并非播放器缓存。`.git` 不通过缓存按钮清理。

## Qwen3-ForcedAligner

之前代码虽使用官方 Transformers 的准备输入和解码接口，但 `language=None` 绕过了日语形态分词，采用通用 CJK 分字。因此不能声称此前完全遵从官方日语调用方式。

用户已批准 nagisa / DyNet 作为文本预处理例外；统一 inference 环境现在固定 nagisa 0.2.11、DyNet38 2.2。声学推理仍用 PyTorch。实际步骤为：

1. 复用已选人声音源，截取完整台词范围；使用去说话人/音效说明后的台词正文，并非直接输入 SRT 文件。
2. 单声道 16 kHz，`prepare_forced_aligner_inputs(..., language="Japanese")`，由官方处理器调用 nagisa、构造音频及词时间模板。
3. 一次模型前向与官方 `decode_forced_alignment`；保留原生词粒度，不均分音素，不需要另跑 ASR。
4. 保存分词结果、处理流程版本与源音频；旧通用分字结果标记待更新，未全量重跑。

两条问题句已在 MPS 跑通；第一句另用 CPU 对照，时间结果与 MPS 完全一致。仍出现零长度词等可疑预测，不能简单归因于 MPS。界面警告并禁止播放零长度区间，原始输出原样保存。跑通不是质量验收。日语字幕不一定逐字忠于音频，强制对齐不会自动纠正这类文本差异。

参考：[官方使用示例](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B-hf)、[官方日语分词实现](https://github.com/QwenLM/Qwen3-ASR/blob/main/qwen_asr/inference/qwen3_forced_aligner.py)。

## Yohane

并非原字幕直接喂入模型：先用 pykakasi 转罗马字，再对齐。所用 NextFire 检查点是日语罗马字卡拉 OK 微调模型，不是专门的日语对白音素模型。

原接入复制了“提前拆音节→CTC token spans→首尾时间”的处理；本次改成上游 `Lyrics` 的词 token 分组，再调用原版 `time_lyrics` 将字符跨度归属到音节，显式 eval/inference mode。神经推理在指定设备，CTC 回溯在 CPU。保存罗马字、实际 token 单位和处理版本，两个问题句已运行。自动罗马字转换仍可能误读专名、助词或表现性长音，不能把它称为人工校对的读音。

参考：[Yohane 原作者流程与限制](https://github.com/Japan7/yohane)、[模型卡](https://huggingface.co/NextFire/mms-300m-ForcedAligner-karaoke-ja-Latn)。

## pydomino：不是缺了某个尾音参数

官方输出按提供的音素序列预测相邻音素的转移时刻，形成连续区间；不会自行往文本音素序列里添加未提供的 `pau`。CTC/转移网络的 blank 也不等于新建停顿标签。当前输入已有首尾 pau 和 G2P 提供的标点停顿。

实际句子「お姉ちゃんが茶道部で それで…」同一已分离音频对照：

| 输入 | min_frame | 第一个「で」的 e | 后接停顿 |
| --- | --- | --- | --- |
| 原正文（G2P 未产生句中 pau） | 1 | 1.38–2.25 s | 无 |
| 原正文 | 3（官方示例） | 1.38–2.25 s | 无 |
| 仅诊断时在「で」后添加逗号，G2P 产生 pau | 1 | 1.38–1.59 s | 1.59–2.19 s |
| 同上 | 3 | 1.38–1.59 s | 1.59–2.19 s |

这说明模型可以在明确停顿音素的约束下给出结束边界；目前问题来自“强制给定序列，不自动发现额外停顿”的能力边界和输入约束共同作用，不是换 10/30 ms 参数能解决。不能一律把字幕空格当停顿，或手动削短所有元音。本次没有改字幕、没有写入诊断版测量、没有新增尾音修正，也没改默认模型。

原始对照保存在 `data/validation/alignment-audit-2026-09-23/pydomino-pause-comparison.json`。

参考：[官方文档](https://dwangomediavillage.github.io/pydomino/)、[区间生成源码](https://github.com/DwangoMediaVillage/pydomino/blob/main/src/domino.cpp)。
